# Spend GPU cycles on robustness, not speed

The GPU earns its place in this project only by doing work the CPU cannot fit into a 20 ms tick. Making the existing single-target IK faster does not count. The strongest, least artificial workload is a **fused CuPy kernel that solves thousands of damped-least-squares IK seeds per frame and picks the one that preserves continuity**, respects the measured joint ranges, and keeps the gripper out of the table. It attacks two problems the repo already documents: IK jumping between solutions, and having no table or self-collision check. The natural second stage is **MPPI over joint accelerations with a short hand-motion prediction**, which reuses the same forward-kinematics code and gives smooth, velocity-limited motion that partly hides pipeline latency. Perception workloads are weaker on this setup. Stereo triangulation is too small to need a GPU. A GPU particle filter over two-camera landmark reprojection is a credible third option, but only if a second webcam is mounted. MANO mesh recovery, TensorRT MediaPipe, fused preprocessing and scene perception are mostly library work, put frames on the wrong side of the Windows/WSL2 boundary, or don't fit 36 hours. Learned policies (ACT) make a good autonomy demo but a weak kernel story. Diffusion Policy has a strong latency story but carries heavy training risk. The pitch judges will believe is "4,096 IK seeds or 1,024 MPPI rollouts per tick in well under a millisecond, which removes flips and table strikes (shown side by side)". Two rules apply to every option: every GPU output still flows through `/arm/<joint>` into `feetech_mirror.py`, whose EEPROM∩SOFT clamps, 2250 ticks/s rate limit and lag/load aborts stay untouched; and the Gazebo world stays ball-only.

## A single 5-DOF solve loses on the GPU, so the pitch must change

The first slide has to survive the question "why a GPU?". The literature answers it bluntly. **At batch size 1, cuRobo's GPU IK takes 2.7 ms against 0.9 ms for CPU TRAC-IK**, and the GPU only pulls ahead from about 10 problems upward. At batch 1000 the picture flips to 27 ms vs 629 ms, about 37,000 solutions/s ([cuRobo](https://arxiv.org/html/2310.17274v2)). GRiD's GPU dynamics kernels shrink from **7.2× faster to 2.5× once I/O is counted** ([GRiD](https://arxiv.org/abs/2109.06976)). NVIDIA's own measurements put a synchronized short-kernel launch at about **9.6 µs per kernel against 2.9 µs of execution** ([NVIDIA CUDA Graphs](https://developer.nvidia.com/blog/cuda-graphs)), and roughly 5 µs for a null launch has been "the standard for the past decade" ([NVIDIA forum](https://forums.developer.nvidia.com/t/launch-of-many-small-kernels-10x-slower-compared-to-one-kernel/350194)). WSL2's GPU paravirtualization layer can only add to that, and nobody has published WSL2-vs-native launch latency on Turing. Measuring it is a cheap, honest first benchmark.

Published teleop systems confirm that IK is not the bottleneck. Bunny-VisionPro measured **retargeting at 2.54 ms and IK-only motion control at 0.74 ms on an i7 CPU** ([Bunny-VisionPro](https://arxiv.org/html/2407.03162v1)). AnyTeleop's slowest module is hand detection, designed for at most 25 Hz ([AnyTeleop](https://arxiv.org/pdf/2307.04577)). A GPU kernel will also be well under 1% of glass-to-motion latency here, since the 30 Hz camera, MediaPipe and the 50 Hz servo bus dominate. So the defensible framing is **more robustness per millisecond**: hundreds to thousands of candidates per tick, scored for quality, with only the winner copied back. The closest research analogue is MIRROR, a **GPU-parallelized differential IK for humanoid teleop** that runs many constrained IK candidates in parallel and keeps the update that makes stable progress past joint limits, singularities and collisions ([MIRROR](https://arxiv.org/abs/2603.23995)). That gives the team a citation showing the idea is real, not a contrivance.

The repo's own state makes the robustness framing concrete. `INTEGRATION.md` records that the IK uses URDF limits rather than the measured usable ranges, so the hardware node "clamps silently, which bends the end-effector path". It also records that there is no self-collision or table check (only a z ≥ −0.05 box), and that `wrist_roll` cannot cross the 0/4095 seam. A multi-seed solver can bake all three in as hard limits or costs. The safety architecture should not change at all: the GPU node publishes `/arm/<joint>` exactly as `ik_node.py` does today, and the hardware node keeps the final clamps, the rate limit and the lag/load aborts. The GPU path also needs a CPU single-seed fallback behind a flag, so a CUDA or WSL hiccup cannot kill the live demo.

## Planning and control workloads give the strongest, most honest kernel story

### Multi-seed IK with continuity selection is the top pick

Batched GPU IK is mature, and the closest benchmark to this team's setup comes from HJCD-IK. It ran on an **RTX 4060 Laptop under Windows 11 + WSL Ubuntu 24.04 with CUDA 12.5** and solved **2,000 Panda IK problems in 8.58 ms**, against 13.97 ms for PyRoki and 30.30 ms for cuRobo ([HJCD-IK](https://arxiv.org/html/2510.07514v1)). That also shows custom CUDA IK kernels work under WSL2. cuRobo fuses all kinematics into **a single CUDA kernel instead of the roughly 125 kernels in STORM's PyTorch version**, and reports kinematics at about 1 ns per query at batch 100k ([cuRobo](https://arxiv.org/html/2310.17274v2)). The SO-101 problem is smaller still: 5 joint transforms, a 6×5 Jacobian and a 5×5 Cholesky solve of (JᵀJ+λ²I). That fits in registers with one thread per seed, the layout the small-matrix literature recommends for n ≤ 8 ([arXiv 2609.15217](https://arxiv.org/pdf/2609.15217)). The fused kernel is about 150 lines of CUDA C. Link transforms and limits live in `__constant__` memory, all iterations loop inside the kernel, and a warp-shuffle argmin picks the winner on the GPU.

What makes this compute-heavy is the selection, not the solve. Each seed is scored with a weighted sum of task error, ‖q − q_prev‖² continuity, distance to the measured soft limits, manipulability and a sphere-collision penalty. Seeds are spread across the elbow and wrist branches. Batching several predicted future hand positions in the same launch adds look-ahead. The user-visible benefit is fewer flips and no stalls on "random restart after failure". Nobody has published flip rates for hand-teleop IK, so the team must measure them, for example by counting frames where ‖Δq‖ exceeds a threshold. The ball-only Gazebo world helps here. `ball_sweep.py` drives a deterministic figure-8 target through `/ball_position`, so CPU and GPU solvers can be compared on identical input with no arm in simulation and no hardware risk. A recorded MediaPipe trace replayed the same way gives the realistic version.

### MPPI with hand prediction is the "wow" second stage

STORM ran joint-space MPPI on a 7-DOF Franka at **125 Hz (under 8 ms per command) with 500 particles × 30 steps** on a Titan RTX, and smooth motion held "even with 200 particles" ([STORM](https://arxiv.org/pdf/2104.13542)). cuRobo's MPPI reached **up to 421 Hz on an RTX 4090** ([cuRobo](https://arxiv.org/html/2310.17274v2)). STORM's key trick was computing the whole batch × horizon of states in one closed-form operation instead of a sequential loop. For a 5-DOF arm at 50 Hz, 1,024–4,096 samples × 20–30 steps is a few hundred thousand FK evaluations per tick. Scaling down from STORM's numbers suggests that is comfortable on a 2060, but nobody has measured it there.

The kernel is one thread per sample rolling out the horizon in registers. It accumulates a cost of tracking error against a predicted hand trajectory, acceleration, jerk, a velocity penalty below the servo's roughly 3,000 ticks/s no-load maximum, and the same collision spheres. A warp-shuffle softmax-weighted reduction and cuRAND or Halton noise finish the update. The visible payoff has three parts: smooth, jerk-limited motion; limits respected by construction rather than by the hardware node's clamp; and latency hiding from a 50–100 ms constant-velocity or Kalman prediction of the hand. STORM's null (zero-acceleration) particles and a short prediction horizon handle sudden hand stops. No paper combines MPPI with hand-motion prediction for teleop latency, so that combination is a novel angle. The main risk is tuning λ, noise σ and cost weights; pytorch_mppi's README itself recommends autotuning ([pytorch_mppi](https://github.com/UM-ARM-Lab/pytorch_mppi)). MPPI's output still goes to `/arm/<joint>`. Its internal velocity limit should sit below the hardware node's 2250 ticks/s so that the hardware rate limit stays a backstop that never fires in normal use. It must never become the only limit.

### Collision checking and reachability maps are cost terms and bonuses, not standalone workloads

cuRobo checks collisions at about **10 ns per query at batch 100k**, up to 16,000× faster than PyBullet ([cuRobo](https://arxiv.org/html/2310.17274v2)). For the SO-101, 10–20 hand-placed spheres plus a table halfspace and one or two box obstacles cost a few hundred FLOPs per configuration. That is real value (the gripper never strikes the table when the hand dips) but too small to justify a GPU by itself, so it belongs inside the IK and MPPI kernels. A learned self-collision MLP and nvblox ESDF maps are overkill without a depth camera. A brute-force reachability/manipulability map is a cheap, embarrassingly parallel bonus taking 2–4 h: run FK over a dense joint grid, atomically reduce into a voxel grid, and use the result to clamp the hand workspace and to show users where the arm can reach. cuRobo uses a similar live reachability visualization of 500 poses at about 15 Hz ([cuRobo](https://arxiv.org/html/2310.17274v2)). Show the voxels as markers or plots. Do not add an arm model to the Gazebo world.

On tooling, **cuRobo itself is a gamble on this machine**. v2 (Apache-2.0 since April 2026) lists "NVIDIA GPU > Turing", which is ambiguous for sm_75, and says nothing about WSL2 ([cuRobo v2 install](https://raw.githubusercontent.com/NVlabs/curobo/main/docs/getting-started/installation.rst)). v0.7.8 supports Volta+ but is research-only licensed ([v0.7.8 LICENSE](https://raw.githubusercontent.com/NVlabs/curobo/v0.7.8/LICENSE)). Using it would also weaken the "custom kernel" claim. Treat it as an optional reference baseline only.

## Perception workloads mostly belong to libraries or the wrong machine

Camera capture and MediaPipe most likely run natively on Windows, with landmarks sent to WSL2, where CUDA works. That boundary decides most perception options: any GPU work on frames needs the frames on the GPU, while only 21 landmarks per view cross into WSL2 cheaply. The transport (UDP, ZMQ, or a small ROS republisher feeding `/ball_position`) is still undecided in `control/CLAUDE.md`, and the team should agree on it rather than have it picked unilaterally.

**Stereo triangulation** is the most useful perception upgrade and the least GPU-shaped. Single-view MediaPipe depth is not metric; multi-view systems discard it and triangulate the 2D joints instead ([V-Hands](https://arxiv.org/pdf/2409.13347)). Two calibrated USB webcams have done this before ([namolert/ComputerVision](https://github.com/namolert/ComputerVision)). The result is a metric wrist position and a real palm normal for wrist pitch. But DLT over 21 points × 2 views is microseconds of CPU math, so a kernel for it would be a gimmick. The GPU-shaped extension is a **particle filter over hand or wrist pose**. Each of 1k–100k particles is scored by its reprojection error against both cameras' landmarks. Weights come from a warp reduction, followed by parallel systematic resampling. It smooths jitter, absorbs the up-to-33 ms skew between unsynchronized webcams via timestamps, and degrades gracefully to one-view likelihood under occlusion. Model-based hand trackers show the likelihood step is the bottleneck: a stereo-RGB tracker reached only **15–20 FPS with 32 particles × 32 generations on a GTX 970**, and the authors note PSO is "inherently parallelizable" ([Back to RGB](https://arxiv.org/pdf/1705.05301)). The landmark-reprojection version needs no renderer, which keeps it feasible in 36 h. Its value depends entirely on a second camera being mounted and calibrated early.

**MANO mesh recovery** produces the most impressive overlay but involves no custom-kernel work and carries high risk. HaMeR ViT-H has **671M parameters, 167 GFLOPs, and runs at 27 FPS on an RTX 4060 Ti**; distilled students reach 40–50 FPS on the same card ([Fast-HaMeR](https://arxiv.org/html/2603.16444v1)). WiLoR publishes no reconstruction FPS, needs MANO registration, is CC-BY-NC-ND, and pins CUDA 11.7 / PyTorch 2.0 ([WiLoR](https://github.com/rolpotamias/WiLoR)). No RTX 20-series numbers or VRAM figures exist, and fp32 ViT-H weights alone would take a large share of 6 GB. **Scene perception** fares worse. nvblox needs RGB-D input and Docker on Ubuntu ([nvblox](https://github.com/nvidia-isaac/nvblox)). EfficientViT-SAM's headline speedup comes from architecture plus TensorRT, not custom kernels ([EfficientViT-SAM](https://arxiv.org/html/2402.05008v2)). Neither adds anything to teleop unless the planner consumes the map.

**MediaPipe on GPU and fused preprocessing** have the weakest payoff. The Python Tasks GPU delegate is Linux/EGL-only and unreliable; issue #5503 reports it failing on Ubuntu ([mediapipe #5503](https://github.com/google-ai-edge/mediapipe/issues/5503)). ONNX ports run with onnxruntime-gpu ([PINTO0309](https://github.com/PINTO0309/hand-gesture-recognition-using-onnx)), but the models are already tiny: **17.1 ms CPU vs 12.3 ms GPU for the full pipeline** on a Pixel 6 ([MediaPipe](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker)). In video mode palm detection runs only on tracking loss. A fused warp-affine + resize + BGR→RGB + normalize + NCHW fp16 kernel is a classic exercise with large micro-benchmark gains: cvGPUSpeedup reports about **38× over chained OpenCV-CUDA calls** ([cvGPUSpeedup](https://github.com/morousg/cvGPUSpeedup)). But the absolute saving on a 224×224 crop is about a millisecond against a 33 ms camera frame, and here the frames live on Windows while the CUDA work lives in WSL2. Do it only as a learning exercise.

## Learned policies offer autonomy, but only diffusion offers a kernel story

LeRobot's own benchmarks (fp32, 10 denoising steps) put **ACT at 5.0 ms and Diffusion Policy at 369.8 ms on an RTX 4090**, with peak memory of 211 MB and 1.12 GB. pi0 needs **13.32 GB** and cannot fit a 6 GB card ([LeRobot paper](https://arxiv.org/pdf/2602.22818)). LeRobot v0.3.3's Diffusion default is **100 DDPM inference steps** ([configuration_diffusion.py](https://raw.githubusercontent.com/huggingface/lerobot/v0.3.3/src/lerobot/policies/diffusion/configuration_diffusion.py)), so on a 2060 the default sampler plausibly takes seconds per chunk. That gives a strong before/after ladder: fp32 eager, then DDIM-10, then AMP fp16, then `torch.compile` with CUDA graphs, then TensorRT, then a fused scheduler-step + GroupNorm/Mish kernel. Fewer steps cost quality, though; Crossway Diffusion sees noticeable drops below about 40 iterations ([Crossway](https://arxiv.org/pdf/2307.01849)). LeRobot's async inference showed that the user-visible metric is task time: SmolVLA on SO-100 dropped from 13.75 s to 9.70 s per episode ([LeRobot paper](https://arxiv.org/pdf/2602.22818)).

The catch is the 36-hour clock. A Classmethod SO-ARM101 run collected **50 episodes in about 45 min and trained ACT for 100k steps in about 7 h** on a DGX Spark. It reached 9/10 success with 30 Hz CUDA inference against 4/10 at 15 Hz on MPS ([Classmethod](https://dev.classmethod.jp/en/articles/lerobot-so-arm101-act-training-eval/)). Turing has no bf16, and no 6 GB training report exists, so a 2060 means overnight training at reduced batch or resolution. Demos recorded through hand-tracking IK will carry its jitter. Diffusion is heavier to train than ACT. ACT is a fine autonomy add-on if a teammate owns it from about hour 12, but its 5–30 ms inference leaves nothing for kernels to fix. Diffusion's latency ladder is the only policy-side GPU story, and it depends on a trained model existing before the final day.

## Present a ladder, a crossover and a side-by-side video

The toolchain choice is settled by Turing support. **Triton dropped Turing after 3.2**, and `tl.dot` on compute capability < 8.0 falls back to FMA without tensor cores ([Triton PR #5066](https://github.com/triton-lang/triton/pull/5066); [triton-windows](https://github.com/woct0rdho/triton-windows)). Triton also suits large tiled tensors, not tiny per-thread problems. **CuPy RawKernel** compiles raw CUDA C through NVRTC with no system nvcc and is the clearest "we wrote a kernel" artifact. NVIDIA Warp supports sm_75, at the floor for its CUDA 13 builds ([Warp compatibility](https://nvidia.github.io/warp/latest/user_guide/compatibility.html)). Numba's CUDA target now lives in `numba-cuda` ([Numba](https://numba.readthedocs.io/en/stable/cuda/overview.html)). Avoid managed memory and large pinned buffers, both of which are limited under WSL2 ([CUDA on WSL](https://docs.nvidia.com/cuda/wsl-user-guide/index.html)).

Profiling works in WSL2 with one setup step. Nsight Compute supports WSL2 on Windows 11 with driver ≥ 525, but **"Access to NVIDIA GPU Performance Counters" must be enabled in the Windows NVIDIA Control Panel** ([Nsight Compute requirements](https://docs.nvidia.com/nsight-compute/ReleaseNotes/topics/system-requirements.html)). Older versions fail with "Profiling is not supported on device 0 … WSL", which version 2023.3 or later fixes ([NVIDIA forum](https://forums.developer.nvidia.com/t/error-profiling-is-not-supported-on-device-0-as-it-uses-the-windows-subsystem-for-linux-wsl/260814)). `nvidia-smi` utilization is unreliable inside WSL2. Time kernels with CUDA events after 50–100 warmup iterations. Time host-inclusive work with `perf_counter_ns` around launch, sync and copy. Report p50/p99 over at least 1,000 samples.

Present four artifacts. The first is an **optimization ladder** in the style of Boehm's SGEMM worklog ([Boehm](https://gwern.net/doc/www/siboehm.com/d4b3e9d6de0655f490fe6369f4d004936248a833.html)). Its steps are: NumPy loop → PyTorch batched (many small kernels) → fused single kernel → SoA layout → in-kernel iterations → GPU argmin with a 5-float copy-back → CUDA graph (cuRobo reports **10× from graphs** ([cuRobo](https://arxiv.org/html/2310.17274))) → an fp16 screening + fp32 polish experiment. Show it as a log-scale bar chart with Nsight occupancy and register counts annotated. The second is an honest **latency-vs-batch crossover plot**, CPU vs GPU, which pre-empts "why GPU?". The third is a **quality metric**: flips per minute, failed frames, peak joint jerk and table penetrations on the identical figure-8 or replayed hand trace, CPU single-seed vs GPU multi-seed vs MPPI. The fourth is a **side-by-side video** plus a 240 fps phone recording of glass-to-motion latency with a per-stage budget bar that shows the GPU's share is tiny. Judges reward a working live demo over slides and want the hardest decision named ([Devfolio](https://guide.devfolio.co/docs/guide/participating-in-hackathons/judging-1)). Here that decision is spending the GPU on candidates rather than speed.

## Ranked recommendation and 36-hour plan

The ranking is: **(1) fused multi-seed IK with continuity selection, measured limits and sphere collision**, which is low risk, directly fixes documented problems, and has the cleanest kernel ladder; **(2) MPPI with hand prediction** on the same FK core, which is the "wow" stage, gated behind a flag; **(3) reachability map**, a 2–4 h visual bonus; **(4) stereo + GPU particle filter**, only with a second webcam and a teammate on the Windows side; **(5) Diffusion Policy latency ladder**, only if a policy track already exists; then **(6) fused preprocessing/TensorRT MediaPipe**, **(7) MANO mesh** and **(8) scene perception**, all of which should be skipped. ACT is an independent autonomy track rather than a GPU workload. The plan below assumes the CPU teleop path already works in sim and the arm homes safely. Every live step uses `feetech_mirror.py` dry run first, then `--live` at low `--max-speed` with the user present.

| Hours | Main track (GPU, WSL2) | Parallel track (Windows/CV) |
|---|---|---|
| 0–2 | Smoke tests: `cupy-cuda12x` RawKernel on the 2060, null-kernel launch microbenchmark, enable perf counters, `ncu` run on a toy kernel | Agree landmark transport to WSL2; MediaPipe CPU → `/ball_position` working |
| 2–6 | NumPy vectorized multi-seed DLS reference with scoring (continuity, measured soft limits, wrist-roll seam); flip/jerk metric harness on `ball_sweep.py` and a recorded hand trace | Record 3–5 hand traces for replay; mount/calibrate 2nd webcam if stereo is planned |
| 6–12 | CuPy ladder v0→v4 (fused kernel, SoA, in-kernel iterations, warp argmin); bit-check against NumPy; `ik_node` `--solver gpu` flag with CPU fallback | Stereo DLT triangulation on CPU (if 2nd camera) |
| 12–15 | Table halfspace + link spheres in kernel; dry-run → low-speed live test; first before/after flip numbers | One-euro filter on CV side; gripper gesture if desired |

| 22–26 | Sleep in shifts; leave an unattended benchmark sweep running | Sleep in shifts |

| 30–32 | **Feature freeze.** Pick the demo config; MPPI ships only if it beats multi-seed IK on metrics | Record side-by-side videos and 240 fps latency clips |

## Conclusion

The question changes from "how do we make this heavier?" to "what does the arm do badly that more candidates would fix?". The repo answers it already: solution jumps, silent clamping at URDF limits, a wrist seam, and no table check. These are search problems, and a GPU is a search engine. That reframing also defuses the strongest objection to the project. Every published number shows a single small IK is faster on a CPU, so the team should concede that openly on a crossover plot and then show the GPU buying quality inside the same 20 ms.

Three uncertainties remain. No one has published batched IK or MPPI timings for a 5-DOF chain on Turing, so all RTX 2060 figures here are extrapolations to replace with day-one measurements. No source quantifies how often hand-teleop IK flips, so the headline metric has to be measured. And MPPI's benefit depends on tuning that can eat the night, which is why multi-seed IK must ship first and stand on its own.
